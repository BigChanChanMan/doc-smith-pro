# 文匠 DocSmith — 打包与部署

## 一句话

`npm run build` 产出 `dist/client`（浏览器资源）+ `dist/server`（SSR handler）两份产物；生产用 `scripts/prod-server.mjs` 把 SSR handler 包成 Node HTTP 服务，不依赖 Vercel/Nitro 等平台运行时。

## 构建

前置：**Node ≥ 22.12**（`@tanstack/react-start` 的 `engines` 要求，Node 20 即使满足 Vite 也跑不了）、npm（仓库用 `package-lock.json`，不是 pnpm）。

```bash
npm ci
npm run build
```

产物结构：

```
dist/
├─ client/assets/     浏览器资源，文件名带内容 hash → 可 immutable 强缓存
├─ server/server.js   SSR 入口，导出 WinterCG fetch handler（default.fetch）
└─ server/assets/     服务端 chunk，按路由切分
```

整个 `dist/` 只有 ~800 KB —— PDF 引擎和中文字体**都不在里面**，见下一节。

## 运行时依赖（部署最容易踩的三个点）

1. **运行必须有 `node_modules`。** `dist/server/server.js` 里 `react`、`@tanstack/react-router`、`h3-v2`、`seroval` 等都是裸导入（构建保留为 external），没有打进 bundle。

2. **PDF 引擎是 `node_modules` 里的 WASM。** `node_modules/takumi-pdf/pkg/takumi_pdf_wasm_bg.wasm`（4 MB），构建不会复制到 `dist/`。反过来也有个好消息：`takumi-pdf` 无 postinstall、无原生二进制，**运行阶段不需要编译工具链**，装生产依赖即可：

   ```bash
   npm ci --omit=dev
   ```

3. **字体按「工作目录」读。** `src/lib/pdf/server-renderer.ts:21`：

   ```ts
   const fontsDir = process.env.FONTS_DIR ?? join(process.cwd(), "fonts");
   ```

   进程的 cwd 必须是有 `fonts/` 的那一层（`fonts/NotoSansSC-Regular.otf`、`fonts/NotoSansSC-Bold.otf`）。systemd 之类的场景改了 `WorkingDirectory` 就会炸，用 `FONTS_DIR` 兜底。

## 启动

| 场景 | 命令 |
|---|---|
| Linux / macOS | `npm start` |
| Windows | `npm run start:win` |
| 不经 npm | `node scripts/prod-server.mjs` |

启动后日志：`[docsmith] 文匠 DocSmith 生产服务已启动: http://0.0.0.0:3000`

入口脚本做两件事：把 `/assets/*` 直接从 `dist/client` 回源（强缓存），其余请求全部转成 `Request` 交给 SSR 的 fetch handler。

> **Windows 为什么要单独的入口**：`prod-server.mjs` 用裸路径 `import(join(DIST, "server", "server.js"))`，而 Node 的 ESM loader 只接受 `file:` / `data:` / `node:` 三种 scheme，Windows 上拿到 `D:\...` 会抛 `ERR_UNSUPPORTED_ESM_URL_SCHEME`。Linux 下路径以 `/` 开头，同样的代码侥幸能跑，所以线上入口不需要改动，Windows 本地/容器用 `prod-server.win.mjs`（唯一差别是 `pathToFileURL()` 转一道）。

### 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `3000` | 监听端口 |
| `HOST` | `0.0.0.0` | 监听地址 |
| `FONTS_DIR` | `<cwd>/fonts` | 字体目录 |
| `NODE_ENV` | — | **设了不生效**：入口脚本内部写死为 `development` |

`NODE_ENV` 那条是历史遗留：脚本顶部（`scripts/prod-server.mjs:8-11`）固定它以避免 SSR 500。实测当前产物引用的是 `react/jsx-runtime`（不是注释里说的 `jsx-dev-runtime`），所以这个 workaround 可能已经过期——想清理的话，改完务必回归 `/themes` 页面（见下）。

## Docker

```bash
docker build -t docsmith:latest .
docker run -d --name docsmith -p 3000:3000 docsmith:latest
```

`Dockerfile` 是多阶段构建：build 阶段装全量依赖跑 `vite build`；runtime 阶段只保留 `npm ci --omit=dev` + `dist/` + `scripts/` + `fonts/`，以非 root 的 `node` 用户运行，`HEALTHCHECK` 每 30s 打一次 `/`。

覆盖端口或字体目录：

```bash
docker run -d -p 8080:8080 -e PORT=8080 -e FONTS_DIR=/app/fonts docsmith:latest
```

镜像里的目录约定（`Dockerfile` 的 `WORKDIR /app` 与字体读取路径必须对齐）：

```
/app
├─ dist/          ← 构建产物
├─ scripts/       ← prod-server.mjs / prod-server.win.mjs
├─ fonts/         ← 运行时按 /app/fonts 读取
└─ node_modules/  ← 生产依赖（含 4MB WASM）
```

## 部署后自检

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/            # 200
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/playground  # 200
```

最有价值的一条是打开 **`/themes`**：它挂载时会服务端批量渲染 9 个真实 PDF，一次覆盖 WASM 加载、字体读取、SSR 整条链路。9 张卡片都出现「📄 查看该主题 PDF →」且没有 `✗` 报错即为正常（本地实测 9/9，无控制台错误）。

## 常见问题

| 现象 | 排查方向 |
|---|---|
| 启动日志正常，但页面 500 | `dist/server/server.js` 的 external 依赖缺失，检查是否漏了 `npm ci --omit=dev` |
| 渲染 PDF 报字体 ENOENT / NotoSansSC | 进程 cwd 不对，或 `fonts/` 没进镜像；用 `FONTS_DIR` 显式指定验证 |
| Windows 上 `ERR_UNSUPPORTED_ESM_URL_SCHEME` | 用成了 Linux 入口，改用 `npm run start:win` |
| `/assets/*` 404 | `dist/client/` 没拷全；该前缀由入口脚本直接回源，不走 SSR |
| 页面能开但很慢 | 确认走的是生产入口而不是 `vite dev`；`NODE_ENV` 被强制为 development 也会带来 dev 版 React 的开销 |
